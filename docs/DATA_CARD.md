# TraceCause data card

## Synthetic fixture track (v1)

**Origin and intended use:** deterministic, wholly simulated MiniShop-style OTLP/JSON traces for parser, graph, retrieval and controlled evaluation development. This is not production telemetry, a privacy-cleared external dataset or a measured benchmark result. The fixtures are generated by `scripts/fixtures.py` with default seed 20261010 and no third-party data. Repository license: see `LICENSE`. Schema version 1.0; generator version is the source revision at the recorded commit. No redaction is needed for these fabricated identities. Public manifest/source hashes and byte counts accompany every episode; evaluator-only truth and semantic hashes live under ignored `data/gold/`.

**Size and split:** 120 episodes in 24 groups, five episodes per group. Train/development/test: 70/25/25 episodes and 14/5/5 groups. Four healthy groups are distributed 2/1/1. The test set uses topology C, absent from training and development. The generated full public dataset is `data/generated/seed-20261010/` and is ignored by Git. A one-episode smoke fixture is committed at `data/fixtures/smoke/`. The generated full index hash is `23c61e47f418517580427a6722403b73c606bab45defab92553b10b14b2eadd7`; the smoke index hash is `82fc0811fe3d148df9ff0aa1e2f58c8f53a9c5cc95722ef8735e5e78281f476d`. Regenerate and verify with `make fixtures-smoke` and `make fixtures`.

**Signals:** server and client spans, explicit status codes, error propagation, latency and traffic-volume changes, partial parentage, duplicate delivery, out-of-order delivery and occasional clock skew. Fault families are service error, service latency, client timeout and volume reduction, plus healthy traffic. The generator deliberately adds unrelated catalog errors. Span timing and requests follow compact synthetic rules; they do not reflect realistic queuing, retries, scaling, saturation, network loss or distributed deployment behavior. Timeout and volume attribution is especially ambiguous. Some spans have missing parents and no complete trace can be assumed.

**Absent signals:** logs, metrics, human incident narratives, actual service resource use, real provider responses, real traffic and production data. `availability_recorded=false`; there is no ingestion-time availability audit in this dataset. The episode time range and baseline are declared in the public manifests. The final question/evidence review is described below. It was performed by the implementation assistant; independent human review is absent.

**Known limitations and prohibited claims:** fixture validity shows that local code can handle controlled structure and faults. It cannot establish fault-location accuracy, causal identifiability, user usefulness, reliability under real failures, security in a deployed environment or generalization to production. The completed frozen evaluation is reported with explicit denominators in EVALUATION_RESULTS.md and does not establish production generalization. The separate MiniShop captured track is documented in `CAPTURE_DATA_CARD.md`; its smoke run is excluded from scored denominators.

**Phase 03 parse quality:** the committed smoke trace source yields 71 unique normalized spans from 72 deliveries; one delivery is an identical duplicate. Its observed missing-parent relationship is flagged. The parser rejects malformed or oversized requests and conflicting duplicates; strict CLI mode emits no spans when there are rejected records. Service identity can remain unresolved, and the allowlist redaction policy intentionally removes arbitrary attributes and dynamic operation names. These are parse-quality properties of the synthetic fixture, not model-performance results. The pinned official OTLP JSON example is stored separately as a conformance fixture.

## Operational knowledge graph track (October 2026)

I captured six separate local incidents on 19 October 2026 by running three small
applications. Their public manifests and source files are committed under
[`data/operational-lab`](../data/operational-lab). Together they contain **28,935
accepted spans, 129 operational receipts and 900 directly linked asynchronous
producer/consumer pairs**. The applications are a synchronous checkout chain, a
parallel news fanout and an upload/queue/worker pipeline. Each has two episodes:
one actual release replacement and one configuration change. I captured 70 seconds
of baseline traffic, 60 seconds under the intervention and 20 seconds of recovery,
with a newer benign entry-service change as a competing lead.

I recorded trace parentage, timestamps, service namespace/environment, release
artifact identity, bounded configuration values and runtime/host metadata.
Operational receipts and traces are separate immutable sources; source hashes and
record offsets bind facts and graph relationships back to their originals. Host
and process IDs describe local processes. I assigned team ownership explicitly;
it was not discovered from a production inventory. The data contains no real
customer requests, personal records or production incidents. This is a controlled
engineering corpus captured from actual running processes, not a synthetic OTLP
generator or a representative production sample.

All six cases are used for a **controlled demonstration evaluation**, not as a
held-out model test. I knew the interventions when designing the deterministic
reasoning policy and froze that policy before the API comparison. The operational
cases are separate from the 50 identifiable episodes used to fit the optional V4
ranker; I did not train that model on these six cases. Minimal reference event
labels and source hashes are published under
[`docs/evaluation/operational/labels`](evaluation/operational/labels-manifest.json).
They are excluded from Docker images and runtime retrieval. Original private
capture controls remain local and are not required to run the public UI.

**Limits:** there are only three hand-built applications, two episodes per
application, one physical host, one prior incident for each second episode,
operator-assigned teams, controlled workloads and ten-second measurement buckets.
There are no independent human incident labels, live customer traffic, independent
availability timestamps, arbitrary message-link chains or evidence of performance
under simultaneous real-world faults. A known intervention is an offline reference
identity, not proof that a graph path establishes causality. I report exact
evaluation denominators and source resolution separately in the README and
[`OPERATIONAL_REASONING.md`](evaluation/OPERATIONAL_REASONING.md).
